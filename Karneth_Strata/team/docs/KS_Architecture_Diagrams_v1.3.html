1. System topology

Top-level view. Operator sits at the Unity client; the Unity client is both the demo environment (simulated swarm) and the operational UI (C2 + SA displays). One PiDog (Raspberry Pi 4B 8GB, 192.168.178.70) on the same LAN closes the hardware-in-the-loop path — proving the UI is not talking only to simulated vehicles. Multi-vehicle architecture (Phase 1+2+3b shipped 2026-04-29) means a second PiDog or a non-PiDog vehicle plugs into the same registry without code changes.

Figure 1 — System topology as of 2026-04-29. Operator drives the Unity client; the Unity client holds C2, SA, the intelligence layer, the simulated swarm, and the multi-vehicle registry. One live PiDog on the LAN closes the HIL path. Purple arrow = Pi-side edge YOLO burst channel (EMCON-survivable). Dashed arrow to 2nd vehicle is where capital + Phase 3a capability gates convert.

2. Detection / ISR data flow

This is the spine of the operator's intelligence picture. Three detector sources publish into a single in-process bus (DetectionBus, main-thread pump, multicast). The bus is consumed locally by the ISR Process Panel and the NEW INTEL badge, and is gated by EmconCommsQueue before going on the wire via DetectionRosPublisher to /swarm/detections on rosbridge. Priority tiers (P0 Critical, P1 High, P2 Low) drive both card ordering and badge counting; Pi-burst cards get a purple border so the operator can tell at a glance which detections survived the EMCON-gated channel.

Figure 2 — Detection / ISR flow. Three detector sources fan into DetectionBus. Local UI subscribers (Process Panel, NEW INTEL badge, evidence-frame swap on the cam panel) read the bus directly. Outbound traffic is gated by EmconCommsQueue so EMCON SILENT cuts the wire without going blind locally. Red dashed arrow = EMCON SILENT assertion severs the rosbridge websocket; queued events are dedupe-released on lift.

3. Multi-vehicle registry & namespacing

Phase 1+2+3b shipped 2026-04-29 (single commit-day, on master). The prior single-Pi assumption — 192.168.178.70 hardcoded across PidogCameraFeed / PidogRosBridge / PidogConnectionMonitor — was retired. VehicleRegistry persists configs to vehicles.json in persistentDataPath; VehicleDiscovery runs a parallel /24 LAN scan that fingerprints PiDog (:8082/health), MAVLink drones (:14550 heartbeat), and generic ROS2 (:9090 rosbridge). The header VehiclePickerPill + VehicleConnectDialog let the operator switch vehicles live; ROS topics are namespaced per vehicle (e.g. /pidog/detections vs /pidog2/detections).

Figure 3 — Multi-vehicle registry. Persistent + StreamingAssets seed feed VehicleRegistry; VehicleDiscovery upserts entries from a parallel /24 scan with 3 fingerprints. Header pill + connect dialog drive operator switching. All Pi-side consumers read Active for IP and call RosTopic(…) for namespaced topics. Phase 3a (capability-gated panels) is the design step that lights up when a non-PiDog vehicle physically arrives.

4. EMCON SILENT — what severs when asserted

EMCON spec lives in Assets/Docs/KS_EMCON_Concept.html; the spec defines three modes (SILENT / BURST / COVERT) plus a Last-Gasp self-destruct. SILENT means zero RF in both directions — not just "stop publishing detections". As of 2026-04-29, asserting EMCON in the Unity client severs every Unity↔Pi channel atomically. The forward-looking default per the spec is SILENT; the operational default today is OPEN until the authority/policy layer drives the transition automatically.

Figure 4 — EMCON SILENT sever points. Operator clicks the header pill; EmconState broadcasts; five Unity-side subscribers each rip their socket / cancel their CTS / force their badge offline within one frame. Pi-side Phase D (LED + TTS cues + YOLO callouts) shipped 2026-04-29; Phase C (Pi-side transmit gate via emcon_gate.py) is pending. BURST / COVERT modes specified in KS_EMCON_Concept.html, not yet wired.

5. PiDog service stack + repo ↔ Pi sync

The live PiDog is repo-managed. Canonical Python lives in the ks_drone repo under pidog/ and is deployed via base64-over-plink (pi-deploy.sh — refuses to run against a dirty repo, prevents aspirational-commit drift) and audited via pi-pull.sh (live tar over plink, diff vs repo, exit-2 on drift). Six runtime units supervise the services: five systemd units (camera / spy / walk / slam / yolo) plus the rosbridge_server Docker container. Pi-side files themselves are not git-tracked; the repo is the source of truth, the Pi is a deployment target.

Figure 5 — PiDog service stack + repo-sync tooling. Repo is source of truth; pi-deploy.sh and pi-pull.sh enforce the invariant. Five systemd services + the rosbridge_server Docker container run on the Pi today. The yolo service was added 2026-04-29 (Slice 7 Phase A); SLAM (amber) is functional mono-SfM with stereo on the roadmap.

6. Comms & security layers

The communications stack is layered by concern: physical link at the bottom, protocol adapters in the middle, authority and cryptography on top. Two paths Pi↔Unity: rosbridge_server WebSocket on Pi:9090 is the primary path (ROS2 native messages tunnelled JSON); HTTP fallbacks exist for camera (MJPEG :8080), audio/level/TTS/LED (:8081), pose/IMU (:8082), SLAM (:8084), YOLO health (:8085). Every fallback is used when rosbridge is disconnected. EMCON SILENT severs both paths.

Figure 6 — Comms & security stack. Top-down: authority/policy → crypto → protocol adapters → physical link. rosbridge WS is now the documented primary path with HTTP fallbacks; EMCON SILENT is shipped on the Unity side and wired through every sever point. BURST / COVERT modes and the Pi-side transmit gate (Phase C) are designed and awaiting capital / hardware.

How to read these diagrams as a DD reviewer

  • Count the purple boxes. Purple is specification-ware — designed, architecturally sound, but not yet shipped. If a category has any green boxes, the foundations are there and capital converts the rest. Phase 3a (capability-gated panels), Pi-side EMCON transmit gate (Phase C), and BURST/COVERT modes are the obvious purple-to-green conversions.
  • Amber means partial. Something runs but is not yet production-grade. SLAM is the live example — Pi-side COLMAP mono-SfM works and produces usable reconstructions; stereo is the next promotion.
  • Dashed arrows are planned flows. Solid arrows are running today. Red dashed arrow in Figure 2 is the EMCON SILENT severance — operationally critical but adversarial to other architecture diagrams that assume always-on links.
  • Scale signals. Figure 1 tells you the operator console is now multi-vehicle, not single-Pi. Figure 2 tells you the intelligence layer is bus-architected with clean source/queue/publisher seams. Figure 5 tells you the Pi is six runtime units with repo-managed deployment, not one hack script.
  • Headline data points. 22 commits on 2026-04-29 (heaviest day in the corpus) shipped: multi-vehicle Phase 1+2+3b, ISR Slice 5+6+7 (sim publisher + EMCON queue + Pi edge YOLO), NEW INTEL badge, evidence-frame swap, P0/P1/P2 priority tiers, Pi-side EMCON LED+TTS cues. Diagrams 1–4 are direct readouts of that day's work.
